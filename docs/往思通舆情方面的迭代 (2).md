## 二、产品定位与差异化

- **形态**：主动型舆情/政策分析工作台 —— 打开即有数据，监测与深度分析在同一处。
- **与数据型竞品（思通舆情等）的差异**：他们输出「发生了什么、有多少条」；本产品输出「这意味着什么、谁在跟谁博弈、接下来会怎样」。广度交给热榜聚合，深度靠三元结构分析与利益关系网络。
- **与通用 AI 的差异**：通用 AI 每次对话给一份文本；本产品有固定方法论、结构化校验、可追溯证据链、可持续追踪的事件档案。
- **不做**：不做全网爬虫集群、不做百万级仿真、不做需登录态的批量个人信息采集。

## 四、功能规格

### 4.1 今日热点 `/today`（R2）

- **用户故事**：早上打开工作台，一屏看到今天政策、经济、科技、社会四个板块的热点，点一条能直接看原文或一键起分析。
- **界面**：顶部分类页签（政策/经济/科技/社会/全部）；每板块卡片列表（排名徽标、标题、来源平台、热度值、时间）；卡片右上角「起分析」按钮 → 跳 `/analysis` 并预填标题。
- **后端**：`GET /api/feed/hotlist?category=&date=`；数据来自 `feed_items` 中 `kind=hotlist` 的当日记录。
- **验收**：本地无任何人工输入时，`/today` 能显示当日 ≥50 条真实热榜条目（配置热榜端点后）。

### 4.2 舆情监测 `/feed`（R3）

- **用户故事**：输入关键词或选择地域/平台，快速筛出相关舆情条目，看清每条的正负面与来源。
- **界面**：左侧筛选栏（时间范围、分类、来源平台、省份/城市、情感、关键词）；中部信息流列表（标题、来源、时间、情感标签、热度、原文链接、地区）；支持分页与 CSV 导出。
- **后端**：`GET /api/feed/items?filters...`；`feed_items` 表提供 `sentiment`（positive/neutral/negative）、`sentiment_score`、`category`、`region_code` 字段。
- **验收**：任一筛选组合 1 秒内返回；情感标签有明确的标注来源（本地模型/词典/LLM 复核）。

### 4.3 监测分析 `/analytics`（R4）

- **用户故事**：看一个时间窗内的整体态势：情绪在变好还是变坏、媒体在说什么、集中在哪些地区。
- **界面**：四宫格 + 一长条
  1. 情感趋势折线（按小时/天，三条线 positive/neutral/negative）
  2. 高频词云（分词 + 停用词过滤）
  3. 来源分布环形图（按平台）
  4. 媒体声量排行（Top 10 站点横向条形）
  5. 行业/分类分布（堆叠柱）
- **后端**：`GET /api/feed/stats?window=&group_by=`，一次返回全部聚合，前端不再多次请求。
- **验收**：所有图表数据来自真实库内条目；无数据时显示空态而非假数据。

### 4.4 舆情地图 `/map`（R5）

- **用户故事**：一眼看清舆情在全国的分布，点省份看该省条目。
- **界面**：全屏中国地图（复用 `report-geo-map` 的底图与合规小窗），着色 = 条目数；右侧省份排行列表；点击省份下钻到市级（有数据时），下方列出该省条目。
- **后端**：`GET /api/feed/geo?level=province|city&window=`；复用 `connectors/regions.py` 的地域识别与既有 GeoJSON。
- **红线**：底图与审图号沿用现有实现，不自行描边；无数据省份灰显，不编数据（继承旧计划第六章第 3 条）。
- **验收**：地图与 `/feed` 同一数据源，筛选条件变化后地图同步。

### 4.5 监测大屏 `/screen`（R6）

- **用户故事**：投屏或展示时用，一屏看到核心指标。
- **界面**：深色全屏，无侧栏；顶部核心指标（今日采集量、负面占比、活跃省份数、预警数）；中部地图 + 趋势；底部热榜 Top10 与最新预警。
- **后端**：复用 `/api/feed/stats` 与 `/api/feed/geo`，增加聚合粒度参数。
- **验收**：全屏下无滚动条、无侧栏；数据 60 秒自动刷新。

### 4.6 舆情预警（R7，继承旧计划 F5/F6/F7）

- **规则**：关键词/正则、分类、地域、情感阈值、热度阈值；组合条件。
- **触发**：命中去重（同规则同条目 6 小时内一次）、静默时间窗、每日上限。
- **通知**：邮件（`email_sender.py` 已有）为第一通道；企微/飞书 webhook 为第二通道（旧计划 F6）。
- **界面**：`/alerts` 事件列表 + 规则管理；侧栏红点。
- **验收**：构造一条命中条目 → 收到邮件 → `/alerts` 可见事件且不重复。

### 4.7 日/周/月报自动生成（R8）

- **用户故事**：不想每天写，系统按时段自动出一份舆情综述，可编辑可导出。
- **实现**：定时任务按行业/地域维度从 `feed_items` 抽取 TopN 条目 → 调用既有生成管线产出报告（Markdown → Word/PDF/HTML）→ 存入报告库（`report_versions` 复用）。
- **与现有报告的关系**：走同一套渲染器，作为新的报告来源类型 `digest`（日报/周报/月报）。
- **验收**：手动触发一次日报告生成，产出物与人工分析报告同格式可下载。

### 4.8 报告增强（R9 + R13）

- **图表内嵌**：报告 HTML/Word/PDF 中插入统计图表（情感趋势、来源分布、地域分布），数据来自该次分析的研究账本；网络图已有，扩展统计图渲染。
- **详细度**：正文要求数据锚点（关键判断落到可查证的量化支撑，继承旧计划「数据锚点」方向）。
- **去 AI 味**：写作约束继续加严；报告文案基调与 README 一致 —— 平实陈述，不排比、不口号（详见第七章红线第 6 条）。
- **数据视图（R13）**：在补齐情感列与时间趋势前，目录中降权；升级后成为「事件数据面板」。

## 五、技术架构

### 5.1 分层

```
采集层  feed_scheduler（每 15~30 分钟）
        ├─ hotlist 热榜聚合（R2，配置驱动，兼容 TrendRadar 输出）
        ├─ rss 订阅源（已有）
        ├─ govdoc 政务公开（已有）
        └─ websearch 定向搜索（已有；按关注词）
             ↓
存储层  feed_items 表（全局舆情流，与任务解耦）
        dedup_key = URL 规范化 + 标题指纹
             ↓
加工层  sentiment.py：本地词典/模型打标为主 → 低置信度走 LLM 复核（BYOK）
        keywords.py：分词 + 停用词 + 词频聚合
             ↓
服务层  routers/feed.py：items / hotlist / stats / geo / alerts
             ↓
展示层  /today /feed /analytics /map /screen（新）
        /dashboard 升级；/analysis /reports /settings 不动
```

### 5.2 数据模型（全部走 `db.py` 幂等 ALTER）

| 表 | 说明 | 关键字段 |
|---|---|---|
| `feed_items`（新） | 全局舆情条目 | id, dedup_key, title, url, source_platform, category, published_at, collected_at, summary, hot_score, sentiment, sentiment_score, sentiment_source, region_code, region_city, region_source, raw_meta(JSON) |
| `alert_rules`（新，继承旧计划） | 预警规则 | id, name, conditions(JSON), channels(JSON), quiet_hours(JSON), daily_cap, enabled |
| `alert_events`（新） | 预警事件 | id, rule_id, feed_item_id, matched(JSON), notified_at, payload(JSON) |
| `feed_collect_runs`（新） | 采集运行记录（排障用） | id, source, started_at, finished_at, fetched, inserted, deduped, error |

不改动：`tasks` / `projects` / `report_versions` / `materials` / `research_monitors` 现有结构（`report_versions` 增 `source_kind` 以区分 digest 报告，可空默认回落旧行为）。

### 5.3 调度

复用 `monitoring.py` 的调度循环模式（每分钟 tick，内部按间隔节流），不引入新框架；采集与既有维护任务（`maintenance.maybe_cleanup`）并列，互不阻塞。单进程部署红线不变。

## 六、数据源与合规（继承旧计划第六章，补充舆情域细则）

1. **数据源分级**（不变）：L1 热榜/RSS/政务公开/搜索（默认开，限速 + robots）；L2 社媒登录态（外部进程、默认关、仅研究用途）；L3 绕过登录/批量个人信息（永不实现）。
2. **热榜来源**：不内置第三方热榜 API 地址（沿用 `hotlist.py` 现有设计），由使用者自持端点配置；文档给出 TrendRadar 兼容格式说明。
3. **情感标注**：本地模型/词典结果必须保留 `sentiment_source`；LLM 复核结果同样标注，便于审计。
4. **版权提示**：聚合展示只存标题/摘要/链接，正文不落地截图或全文转载；对外商用前确认新闻信息转载资质要求。
5. **地图合规**：同旧计划第六章第 3 条（同一份标准底图 + 审图号 + 南海诸岛小窗）。
6. **零回归**：所有新功能以新表、新路由、新页面实现；旧接口签名不变；每个里程碑合入前跑后端全量 pytest + 前端构建 + `体检.bat`。

## 九、风险与红线

1. **采集稳定性**：热榜端点由使用者自持，端点失效时页面降级显示「暂无数据 + 原因」，不静默、不编数据。
2. **情感准确性**：词典/模型打标必然有误判，界面标注数据来源，并提供人工覆盖入口（M2 可选）。
3. **成本**：LLM 只用于低置信度复核与报告生成，避免全量标注导致 BYOK 额度消耗失控。
4. **性能**：SQLite 单文件在十万级条目内可用；`feed_items` 需建 `(collected_at)`、`(category)`、`(region_code)` 索引；超量后评估归档策略。
5. **合规**：见第六章；深爬（M5）必须单独评审后启动，默认永不开启。
6. **文案红线（本次新增）**：新增界面与文档文案一律平实陈述 —— 不排比、不口号、不故作姿态（对齐 2026-09-20 README 修订确定的口径）。
7. **不破坏 BYOK**：舆情侧不引入任何服务端密钥。
